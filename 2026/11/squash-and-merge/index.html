squash and merge

2026/11/26

开发方式

我的开发方式。主要是有两个分支，dev 分支和 master 分支。master 分支是生产使用，dev 分支是开发使用。

每个大变更都会新起一个 dev 分支，我用 dev 统称所有的开发分支。

dev 开发好后，测试没问题，就可以进行 dev->master PR 生成，没有什么问题就合并。

问题背景

但是今天遇到一个问题

例如在 dev 分支进行了 3 个提交

1 -> 2 -> 3(dev)

现在把 3 个提交推送到生产：dev -> master pr

1 -> 2 -> 3

发布完毕之后我又在 dev 上开发了 4 和 5 两个提交

1 -> 2 -> 3 -> 4 -> 5(dev)

再次推上生产：dev -> master pr

预期合并列表应该是

4 -> 5

但是这次获得的提交列表却是

1 -> 2 -> 3 -> 4 -> 5

上个 pr 已经合并过的 commit 在这次又出现了，很奇怪。

搜索了下，这种结果是 squash 导致的。

我想起在 Linear 中我是使用按钮 Squash and Merge 来合并的。

squash 效果

1 -> 2 -> 3(master)

1 -> 2 -> 3 -> 4 -> 5(dev)

进行了 squash 之后就会

  1. 算出净改动：4 -> 5 的总体变更
  2. 取到 master 工作区，在 master 分支重新生成一个提交
  3. 至于 4 -> 5 这些 commit 历史，则不会合并到 master 分支

不要用这种方式去进行 pr 的交互。

我一开始没有想起来这个名词。

但其实我很久之前就已经在本地使用过的。

commit1 更新应用配置 1
commit2 更新应用配置 2
commit3 更新应用配置 3
commit4 更新应用配置 4

因为这些零零碎碎的很占据注意力，我一般都会把这 4 个全部压缩为 1 个 commit，这样就会减少很多细节的展示了。

Linear 中 merge 策略

https://linear.app/docs/code-and-reviews

在 Linear 中可以去选择对应的 merge 策略，更新为你习惯使用的方式即可。
